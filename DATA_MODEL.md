# DATA_MODEL.md --- JainConnect Data Model

**Status:** Proposed logical data model\
**Database direction:** PostgreSQL + Prisma\
**API prefix:** `/api/v1`

This document defines the proposed entities, relationships, lifecycle
states, privacy boundaries, and integrity rules for JainConnect. It is a
design baseline, not evidence that these tables or models already exist.
Before implementation, compare it with the repository, `PRD.md`,
`ARCHITECTURE.md`, and any existing Prisma schema. Preserve existing
data and migrations.

## 1. Modeling Principles

1.  PostgreSQL is the primary source of truth for application records.
2.  Every entity must have a clear owner, visibility rule, lifecycle,
    and deletion/retention policy.
3.  Use stable IDs, foreign keys, unique constraints, and indexes rather
    than relying on UI-only rules.
4.  Store only the personal data required for a defined product purpose.
5.  Treat donor contact information, blood requests, and verification
    evidence as sensitive or restricted.
6.  Public content must not become visible or indexable until it meets
    the relevant review and publication rules.
7.  Temple/trust donation instructions and JainConnect support must use
    distinct data models and authorization paths.
8.  Record who performed sensitive actions and when, without copying
    sensitive payloads into audit logs.
9.  Prefer explicit status fields and timestamps over inferring status
    from the presence or absence of other fields.
10. Use UTC for stored timestamps; render dates and times in the user's
    or event's relevant timezone.
11. Avoid polymorphic relationships that cannot be protected with
    database constraints unless there is a documented reason.
12. Use synthetic data in development and tests. Never seed real donor
    or verification data.

## 2. ID, Time, and Common Fields

Recommended defaults:

-   Primary key: UUID, generated by the application or database
    consistently.
-   Timestamps: `createdAt`, `updatedAt` in UTC.
-   Actor fields: `createdById`, `updatedById` where accountability is
    required and a user relationship is appropriate.
-   Slugs: unique within the relevant public resource type.
-   Lifecycle: explicit enums or constrained status values.
-   Money: integer minor units plus an ISO currency code if financial
    amounts are ever recorded. Never use floating-point values for
    money.
-   Locations: structured, privacy-aware fields. Do not store exact
    coordinates for donors unless there is a documented, consented need.
-   JSON: use only for genuinely flexible metadata, not as a substitute
    for core relational structure.

A common `Base` model is shown conceptually below; Prisma does not
require inheritance, so fields should be repeated or generated using the
project's established conventions.

``` prisma
model Example {
  id        String   @id @default(uuid()) @db.Uuid
  createdAt DateTime @default(now()) @db.Timestamptz(6)
  updatedAt DateTime @updatedAt @db.Timestamptz(6)
}
```

Use the database's actual UUID representation and naming conventions
consistently across all models.

## 4. Identity, Accounts, and Permissions

### 4.1 `User`

Purpose: authentication identity and account lifecycle.

Suggested fields:

-   `id`
-   `email` nullable if another verified sign-in method is used; unique
    when present
-   `phone` nullable; unique only if verified and required by the
    authentication design
-   `displayName`
-   `status`: `PENDING`, `ACTIVE`, `SUSPENDED`, `DELETION_REQUESTED`,
    `DELETED`
-   `emailVerifiedAt`, `phoneVerifiedAt`
-   `lastLoginAt` where operationally needed
-   `createdAt`, `updatedAt`, `deletedAt` where retention rules require
    it

Rules:

-   Do not store plaintext passwords. If local password authentication
    is implemented, store only a strong, appropriately salted password
    hash using a maintained password-hashing library.
-   Do not assume that email or phone is verified because a value
    exists.
-   Avoid exposing authentication identifiers in public APIs.
-   Define account deletion, recovery, and retention behavior before
    production.

### 4.2 `UserProfile`

Purpose: optional public/member profile separate from authentication
data.

Suggested fields:

-   `id`, `userId` (unique foreign key)
-   `displayName`
-   `avatarObjectKey` or approved image reference
-   `city`, `state`, `country` when voluntarily supplied
-   `bio` with length limits
-   `visibility`: `PRIVATE`, `COMMUNITY`, `PUBLIC`
-   `createdAt`, `updatedAt`

Do not place donor status, blood group, private phone number, identity
evidence, or authentication details in the general public profile.

### 4.3 `Role`, `Permission`, and assignments

Suggested logical tables:

-   `Role`: stable key, display name, description
-   `Permission`: stable key and description
-   `RolePermission`: many-to-many join
-   `UserRole`: `userId`, `roleId`, optional scope/organization
    reference, assigned by, assigned at, revoked at

Possible role keys include `MEMBER`, `CONTENT_EDITOR`, `VERIFIER`,
`MODERATOR`, and `ADMIN`. Final roles and permissions must follow
`PRD.md`.

Rules:

-   Enforce permissions on the server for each action and resource.
-   Organization-scoped access must be scoped to a verified organization
    membership.
-   Do not trust role or owner IDs from a client request.
-   Log role grants and revocations as audit events.

### 4.4 `ConsentRecord`

Purpose: retain a traceable record of explicit consent for specific
purposes.

Suggested fields:

-   `id`, `userId`
-   `purpose`: e.g. `BLOOD_DONOR_LISTING`, `CONTACT_SHARING`,
    `NOTIFICATIONS`, `ANALYTICS`
-   `policyVersion`
-   `status`: `GRANTED`, `WITHDRAWN`
-   `grantedAt`, `withdrawnAt`
-   `source` (web, mobile, admin-assisted where allowed)
-   Minimal metadata required to establish the consent event

Do not treat general terms acceptance as consent for blood-donor
participation or contact sharing. A withdrawn consent must be enforced
by the application immediately, not merely stored for reference.

## 5. Organizations, Temples, Trusts, and Representatives

### 5.1 `Organization`

Purpose: shared identity for a temple trust, community organization, or
other eligible organization.

Suggested fields:

-   `id`, `name`, `slug`
-   `organizationType`: `TEMPLE_TRUST`, `COMMUNITY_GROUP`, `CHARITY`,
    `OTHER`
-   `description`
-   `publicEmail`, `publicPhone`, `websiteUrl`
-   `addressLine1`, `addressLine2` only when intended for public display
-   `city`, `state`, `postalCode`, `country`
-   Optional public coordinates for map display, subject to verification
-   `verificationStatus`: `PENDING`, `VERIFIED`, `REJECTED`,
    `SUSPENDED`, `NEEDS_REVIEW`
-   `publicationStatus`: `DRAFT`, `PUBLISHED`, `UNPUBLISHED`, `ARCHIVED`
-   `verifiedAt`, `verifiedById`
-   `createdById`, `createdAt`, `updatedAt`

Rules:

-   Verification and publication are separate concepts.
-   Public details must be reviewed and accurate.
-   Do not publish submitted verification evidence.
-   Changes to high-risk fields should trigger re-review.

### 5.2 `OrganizationMember`

Purpose: associate a user with an organization and scoped permissions.

Suggested fields:

-   `id`, `organizationId`, `userId`
-   `membershipRole`: `OWNER`, `MANAGER`, `EDITOR`, `VIEWER`
-   `status`: `PENDING`, `ACTIVE`, `REVOKED`
-   `approvedById`, `approvedAt`, `createdAt`

Constraints:

-   Unique active membership for a given organization/user pair,
    implemented with an appropriate database strategy.
-   Membership alone must not automatically confer verified status on
    the organization.
-   Sensitive organization edits may require renewed review.

### 5.3 `Temple`

Purpose: temple-specific public content, linked to an organization where
applicable.

Suggested fields:

-   `id`, `organizationId` nullable only if standalone temple records
    are explicitly supported
-   `name`, `slug`
-   `traditionOrLineage` where relevant and verified
-   `description`, `history`
-   Public address, city, state, country, timezone
-   Public contact and website
-   `darshanInformation`, accessibility details, visitor guidance
-   `verificationStatus`, `publicationStatus`
-   `lastReviewedAt`, `createdAt`, `updatedAt`

Use tradition-aware, neutral language. Do not infer religious
affiliation, lineage, or endorsement from a name or image.

### 5.4 `Trust`

Purpose: trust-specific profile, legal/organizational details, and
public service information.

Suggested fields:

-   `id`, `organizationId`
-   `name`, `slug`, `description`
-   Public contact and website
-   `registrationReference` only if appropriate and verified; restrict
    access if not public
-   `verificationStatus`, `publicationStatus`
-   `lastReviewedAt`, `createdAt`, `updatedAt`

Do not expose private identity documents or unverified registration
claims.

### 5.5 `VerificationReview`

Purpose: controlled review history for organizations and other supported
records.

Suggested fields:

-   `id`
-   Target type and target ID, or preferably separate typed review
    tables when relational integrity requires it
-   `submittedById`, `reviewerId`
-   `status`: `PENDING`, `APPROVED`, `REJECTED`, `NEEDS_MORE_INFO`
-   `reviewNotes` with strict access control
-   `evidenceObjectKeys` stored in a restricted evidence model or
    private object storage
-   `submittedAt`, `reviewedAt`

For strong relational integrity, use a shared `VerificationCase` linked
to an `Organization`, `Temple`, or `Trust` through explicit nullable
foreign keys with a constraint that exactly one target is set, or use
separate typed tables. Do not use an unconstrained polymorphic target
without documenting the trade-off.

## 6. Community Directory and Places

### 6.1 `CommunityListing`

Optional generic listing for approved community services not represented
by a more specific entity.

Suggested fields:

-   `id`, `organizationId` nullable if individually managed listings are
    supported
-   `name`, `slug`, `category`
-   `description`
-   Public contact and website
-   Public address and approximate coordinates
-   `verificationStatus`, `publicationStatus`
-   `createdById`, `lastReviewedAt`, timestamps

Use specialized tables when a category has distinct behavior,
permissions, or lifecycle rules. Avoid putting every domain into an
untyped `type + JSON` record.

### 6.2 `Bhojanalay`

Purpose: discover Jain food services and relevant dietary information.

Suggested fields:

-   `id`, optional `organizationId`
-   `name`, `slug`, `description`
-   Public address, city, state, country, coordinates
-   Public contact, opening hours, website
-   `foodInformation` and meal/service notes
-   `verificationStatus`, `publicationStatus`, `lastReviewedAt`
-   timestamps

Do not assert that a kitchen is Jain-compliant, open, or currently
serving a specific menu unless there is a reliable basis and review
date.

### 6.3 `Dharamshala`

Purpose: lodging and visitor information.

Suggested fields:

-   `id`, optional `organizationId`
-   `name`, `slug`, `description`
-   Public address, location, contact, website
-   Public booking/contact instructions
-   Accessibility and facility information where verified
-   `verificationStatus`, `publicationStatus`, `lastReviewedAt`
-   timestamps

Do not imply real-time room availability unless an actual availability
integration exists.

### 6.4 `PilgrimagePlace`

Purpose: pilgrimage destination details.

Suggested fields:

-   `id`, optional `organizationId`
-   `name`, `slug`, `description`, `historicalContext`
-   Public address and coordinates
-   Visitor guidance, access notes, official links
-   Relevant tradition/lineage fields where sourced
-   `verificationStatus`, `publicationStatus`, `lastReviewedAt`
-   timestamps

## 7. Gurus, Resources, and Media

### 7.1 `Guru`

Purpose: sourced public profile for a spiritual teacher or guru.

Suggested fields:

-   `id`, `name`, `slug`
-   `traditionOrLineage` where reliably sourced
-   `biography`, `officialWebsite`
-   Approved public photo reference
-   `verificationStatus`, `publicationStatus`, `lastReviewedAt`
-   timestamps

Rules:

-   Do not invent titles, affiliations, lineage, biography, or
    endorsements.
-   Distinguish facts, attributed statements, and editorial
    descriptions.
-   Respect corrections and takedown requests.

### 7.2 `MediaResource`

Purpose: authorized pravachan, official livestream, darshan stream,
recording, or other media reference.

Suggested fields:

-   `id`, `title`, `slug`, `description`
-   `mediaType`: `LIVE_STREAM`, `VIDEO`, `AUDIO`, `ARTICLE`,
    `EXTERNAL_LINK`
-   `provider`
-   `externalUrl` or approved internal object key
-   Optional `guruId`, `templeId`, `organizationId`
-   `authorizationSourceUrl` or rights/permission reference where
    relevant
-   `publicationStatus`: `DRAFT`, `PUBLISHED`, `UNPUBLISHED`, `ARCHIVED`
-   `startsAt`, `endsAt` for scheduled streams/events when applicable
-   `lastReviewedAt`, `createdById`, timestamps

Validate allowed URL schemes and hosts. Do not scrape or re-host content
without authorization. Never embed arbitrary untrusted HTML.

### 7.3 `Resource`

Purpose: articles, books, official links, guides, calendar references,
and other curated information.

Suggested fields:

-   `id`, `title`, `slug`, `summary`
-   `resourceType`, `language`
-   `sourceName`, `sourceUrl`, attribution
-   `content` only where publishing rights permit
-   `publicationStatus`, `lastReviewedAt`, `createdById`, timestamps

Track the source and review date for time-sensitive information.

## 8. Events and Calendar

### 8.1 `Event`

Suggested fields:

-   `id`, `title`, `slug`, `summary`, `description`
-   `eventType`
-   `organizerOrganizationId` nullable where applicable
-   `templeId` nullable where applicable
-   `locationName`, public address, online event URL if approved
-   `startsAt`, `endsAt` as timezone-aware timestamps
-   `timezone` as an IANA timezone identifier
-   `publicationStatus`: `DRAFT`, `PENDING_REVIEW`, `PUBLISHED`,
    `CANCELLED`, `ARCHIVED`
-   `verificationStatus` where required
-   `sourceUrl`, `lastReviewedAt`, `createdById`, timestamps

Constraints and behavior:

-   Validate `endsAt` is later than `startsAt`.
-   Distinguish cancelled events from expired events.
-   Show the event's local time and timezone to users.
-   Update public status when the organizer reports a change; do not
    imply real-time accuracy without verification.
-   Only eligible published events should enter the sitemap or
    structured data.

### 8.2 `CalendarEntry`

Purpose: curated Jain calendar dates and explanatory resources.

Suggested fields:

-   `id`, `title`, `slug`, `date`
-   `traditionOrCalendarSystem` when relevant
-   `description`, `language`, `sourceUrl`
-   `publicationStatus`, `lastReviewedAt`, timestamps

Religious observances may vary by tradition, region, or calendar
convention. Do not model one interpretation as universal when reliable
sources indicate variation. Store source attribution and applicable
context.

### 8.3 `EventReminder`

Purpose: opt-in reminder subscriptions.

Suggested fields:

-   `id`, `eventId`, `userId`
-   `channel`: `PUSH`, `EMAIL`
-   `scheduledFor`, `status`: `PENDING`, `SENT`, `CANCELLED`, `FAILED`
-   `deduplicationKey`, timestamps

Constraints:

-   Unique user/event/channel reminder where appropriate.
-   Respect notification preferences and event cancellation.
-   Avoid sensitive content in reminder payloads.

## 9. Blood Network

### 9.1 `DonorProfile`

Purpose: sensitive record for a user who explicitly opts into the blood
network.

Suggested fields:

-   `id`, `userId` (unique foreign key)
-   `bloodGroup` using a controlled enum or validated set
-   `city`, `region`, `state` as broad location fields
-   `availabilityStatus`: `AVAILABLE`, `PAUSED`, `UNAVAILABLE`,
    `WITHDRAWN`
-   `consentRecordId` or a reference to the active consent record
-   `contactMethodPreference`
-   `lastConfirmedAt`, `expiresAt`
-   `createdAt`, `updatedAt`, `withdrawnAt`

Avoid storing exact home address or public coordinates. Do not store
medical history unless a specific, reviewed, consented requirement
exists.

Access rules:

-   Public endpoints must not return donor profiles or contact
    information by default.
-   Search results should reveal only the minimum approved fields.
-   Contact details require explicit permission and an approved contact
    workflow.
-   Consent withdrawal must disable discovery and contact access
    promptly.
-   Expired or stale records must be excluded from active results.

### 9.2 `BloodRequest`

Purpose: time-bounded request for blood-donation assistance.

Suggested fields:

-   `id`, `createdById`
-   `bloodGroup`
-   `city`, `region`, `hospitalName`
-   Hospital/contact details only to the extent needed and with an
    appropriate disclosure rule
-   `unitsNeeded` only if required and responsibly sourced
-   `neededBy`, `expiresAt`
-   `status`: `PENDING_REVIEW`, `ACTIVE`, `FULFILLED`, `CANCELLED`,
    `EXPIRED`, `REJECTED`
-   `verificationStatus` or review state where required
-   `publicSummary` that excludes private details
-   `createdAt`, `updatedAt`, `closedAt`

Rules:

-   Validate the request and define moderation rules before public
    display.
-   Expire requests automatically or through a reliable scheduled
    process.
-   Do not expose requester phone numbers or private medical information
    publicly.
-   Provide report, cancellation, and correction paths.
-   The platform is not a medical authority and must not guarantee
    compatibility or outcomes.

### 9.3 `BloodRequestContact` or `ContactRequest`

Purpose: controlled contact between an authorized requester and a donor
or responder.

Suggested fields:

-   `id`, `bloodRequestId`
-   `requesterUserId`, `donorUserId`
-   `status`: `PENDING`, `ACCEPTED`, `DECLINED`, `CANCELLED`, `EXPIRED`
-   `initiatedAt`, `respondedAt`, `expiresAt`
-   Minimal audit metadata

Do not expose unrestricted donor lists. Define contact limits, abuse
controls, and consent before enabling direct contact.

## 10. Seva, Charity, and Reporting

### 10.1 `SevaInitiative`

Purpose: verified public information about a community service or
charity initiative.

Suggested fields:

-   `id`, `organizationId` where applicable
-   `title`, `slug`, `summary`, `description`
-   `category`, location and dates where relevant
-   `officialUrl`
-   `verificationStatus`, `publicationStatus`, `lastReviewedAt`
-   timestamps

Do not imply that JainConnect receives or manages funds unless a
separately reviewed, explicitly documented flow exists.

### 10.2 `Report`

Purpose: user reports of inaccurate, fraudulent, unsafe, or unauthorized
content.

Suggested fields:

-   `id`, `reporterUserId` nullable for anonymous reports if supported
-   Explicit target foreign key(s), such as `organizationId`, `eventId`,
    `mediaResourceId`, `bloodRequestId`
-   `reasonCode`, short `description`
-   `status`: `OPEN`, `IN_REVIEW`, `ACTIONED`, `DISMISSED`
-   `assignedToId`, `resolutionCode`, `resolvedAt`
-   timestamps

For referential integrity, prefer typed nullable target columns with a
constraint requiring exactly one target, or separate report tables per
domain. Do not rely on an unconstrained `targetType + targetId` pair
without a documented integrity strategy. Restrict access to report
details.

### 10.3 `ContentSubmission`

Purpose: track proposed or user-submitted public content before
publication.

Suggested fields:

-   `id`, `submittedById`
-   Typed target or submission payload with validated schema
-   `status`: `DRAFT`, `SUBMITTED`, `IN_REVIEW`, `APPROVED`, `REJECTED`,
    `NEEDS_CHANGES`
-   `reviewerId`, `reviewNotes`, `submittedAt`, `reviewedAt`
-   timestamps

If JSON is used for submission payloads, validate it against a versioned
schema and convert approved records into typed domain tables. Never
expose internal reviewer notes publicly.

## 11. Donations and Platform Support --- Separate Domains

These are intentionally distinct models. Do not use a shared generic
donation table that can confuse recipients or combine permissions and
reporting.

### 11.1 `TempleDonationInstruction`

Purpose: verified instructions for paying a specific temple or trust
directly.

Suggested fields:

-   `id`
-   `organizationId` and/or `templeId` with clear constraints ensuring
    the intended recipient
-   `recipientDisplayName`
-   `paymentMethod`: `UPI_QR`, `OFFICIAL_PAYMENT_URL`, `BANK_TRANSFER`,
    `OTHER_APPROVED`
-   `qrObjectKey` or approved payment URL; avoid public arbitrary
    external image URLs
-   `recipientIdentifier` only where safe and appropriate for display
-   `purposeDescription`
-   `verificationStatus`: `PENDING`, `VERIFIED`, `REJECTED`,
    `SUSPENDED`, `NEEDS_REVIEW`
-   `publicationStatus`: `DRAFT`, `PUBLISHED`, `UNPUBLISHED`
-   `verifiedById`, `verifiedAt`, `lastReviewedAt`
-   `validFrom`, `validUntil` where useful
-   timestamps

Rules:

-   Verify the organization, representative authority, recipient
    identity, and payment destination before publication.
-   Changes to QR or payment identifiers must require review.
-   Keep verification evidence private.
-   Do not store payment credentials or imply that JainConnect processes
    these funds.
-   A QR scan or external redirect is not a payment confirmation.

### 11.2 `PlatformSupportConfig`

Purpose: controlled configuration for optional JainConnect
operating-cost support.

Suggested fields:

-   `id`
-   `enabled`
-   `displayLabel`, `purposeDescription`
-   `paymentMethod`, approved QR object key or official payment URL
-   `recipientLegalName` where applicable
-   `reviewStatus`, `reviewedById`, `reviewedAt`
-   `updatedById`, timestamps

Only authorized administrators may modify this configuration. Public
display must be disabled until recipient and legal/accounting
requirements are reviewed.

### 11.3 `PlatformSupportRecord`

Purpose: optional record of a user's declared or confirmed support
action, if recording is actually required.

Suggested fields:

-   `id`, optional `userId`
-   `supportMethod`
-   `amountMinor` and `currency` only if a trustworthy amount is
    provided
-   `status`: `INITIATED`, `PENDING_CONFIRMATION`, `CONFIRMED`,
    `FAILED`, `CANCELLED`, `UNKNOWN`
-   Provider reference only if generated by a trusted integration
-   `confirmedAt` only when confirmed through an authoritative source
-   timestamps

If the platform merely displays a QR and cannot verify payment, do not
create a false `CONFIRMED` record. Prefer no transaction record or an
explicitly unverified user declaration. Do not imply a receipt, tax
benefit, or payment success without evidence.

### 11.4 Donation/support invariants

-   Temple/trust donation instructions and platform support must not
    share recipient IDs implicitly or share public labels.
-   The platform must not route temple/trust donations through its own
    operating account.
-   Declining platform support must not reduce access to core features.
-   Use separate permissions, routes, admin views, and analytics
    dimensions.
-   Record who approved or changed payment instructions and when.
-   Review applicable legal, accounting, and tax requirements before
    accepting or collecting funds.

-   `id`, `userId`
-   `channel`: `PUSH`, `EMAIL`
-   `category`: `EVENT_REMINDER`, `ACCOUNT_SECURITY`, `SERVICE_UPDATE`,
    `COMMUNITY_UPDATE`
-   `enabled`
-   timestamps

### 12.2 `NotificationDelivery`

Suggested fields:

-   `id`, `userId`
-   `channel`, `templateKey`
-   `status`: `QUEUED`, `SENT`, `FAILED`, `CANCELLED`
-   `deduplicationKey`
-   Provider message ID where safe
-   `scheduledAt`, `sentAt`, `failedAt`
-   Minimal failure code and timestamps

Do not log full message bodies containing private details. Ensure

## 13. Audit Events

### 13.1 `AuditEvent`

Purpose: accountability for sensitive operations.

Suggested fields:

-   `id`
-   `actorUserId` nullable for system jobs
-   `action` stable key, such as `ORGANIZATION_VERIFIED`,
    `ROLE_REVOKED`, `DONATION_INSTRUCTIONS_SUSPENDED`
-   `targetType`, `targetId` with documented integrity strategy
-   `summary` safe for authorized audit readers
-   `correlationId`
-   `createdAt`

Rules:

-   Audit events should be append-only to ordinary application roles.
-   Avoid recording passwords, tokens, donor contact details, uploaded
    evidence, full request bodies, or payment secrets.
-   Restrict access and define retention.
-   For important events, use typed references or an integrity strategy
    that can be checked.
-   Do not rely on audit events as a replacement for the authoritative
    state in domain tables.

  `PlatformSupportRecord`             Index on status and creation time;
                                      unique trusted provider reference
                                      where applicable

  `NotificationDelivery`              Unique deduplication key; index on
                                      status and scheduled time

  `AuditEvent`                        Index on actor, target, action, and
                                      creation time
  -----------------------------------------------------------------------

Additional rules:

-   Normalize searchable email/phone values consistently, without
    logging them.
-   Use partial unique indexes or a clear active-record model where
    uniqueness applies only to active rows.
-   Use database constraints for valid date ranges and mutually
    exclusive target references when feasible.
-   Choose full-text or trigram search only after assessing actual needs
    and privacy implications.
-   Do not store a search index containing sensitive donor contact
    information.

## 15. Lifecycle and Retention

Define retention before production for:

-   Deleted or suspended user accounts.
-   Withdrawn donor profiles and consent history.
-   Expired blood requests and contact requests.
-   Verification evidence and review notes.
-   User reports and moderation records.
-   Notification delivery records.
-   Audit events.
-   Temporary uploads and unapproved submissions.
-   Optional support records and any payment-provider references.

Recommended behavior:

-   Expired blood requests disappear from active discovery and cannot be
    reopened without a new validation/review step.
-   Withdrawn donor profiles are removed from search immediately; retain
    only the minimum consent/audit history legally and operationally
    required.
-   Deleted accounts should have personal data removed or anonymized
    where feasible and appropriate, while retaining legally required or
    security-relevant records under a documented policy.
-   Private evidence should have a defined retention period and
    restricted deletion permissions.
-   Avoid indefinite retention by default.

Exact retention durations require product, legal, and operational
decisions; do not invent them silently.

## 16. Search and Public Indexing

Searchable public entities may include published and appropriately
verified:

-   Organizations, temples, trusts
-   Gurus and approved media resources
-   Events and calendar resources
-   Bhojanalays, dharamshalas, pilgrimage places
-   Approved community listings and seva initiatives

Do not index:

-   User-private profiles or account pages
-   Donor profiles or contact requests
-   Blood-request contact details or sensitive request payloads
-   Verification evidence and internal review notes
-   Admin pages, pending submissions, private reports
-   Draft, rejected, suspended, or empty pages

Search APIs must enforce visibility and authorization independently of
whether a record is in a search index. Removing a record from a sitemap
is not an access-control measure.

## 17. Prisma Implementation Guidance

This document is logical guidance, not a complete ready-to-run Prisma
schema. Before implementing models:

1.  Inspect the existing Prisma version, schema, migration history,
    naming conventions, and database state.
2.  Map the PRD's user roles and acceptance criteria to concrete
    relationships.
3.  Decide whether organization, temple, and trust records should be
    separate tables, shared tables with typed extensions, or both.
4.  Decide the authentication/session strategy.
5.  Define enums and deletion/retention policies.
6.  Implement one reviewed migration at a time.
7.  Add database constraints, indexes, and tests for sensitive
    invariants.
8.  Generate and validate Prisma Client using the repository's existing
    scripts.
9.  Test migrations against a disposable or staging database before
    production.
10. Document any deviation from this model and the reason.

Do not generate all models in one unreviewed migration. Implement
incrementally and preserve compatibility with existing data.

## 18. Open Decisions Before Production

The following require explicit decisions:

-   Final authentication provider and session/token model.
-   Whether users can sign in with email, phone, or both.
-   Final role/permission matrix and organization-scoped access.
-   Exact public/private profile fields.
-   Blood donor contact workflow and expiry intervals.
-   Verification evidence requirements and retention.
-   Final event and Jain calendar source-of-truth policy.
-   Media authorization/review workflow.
-   Whether platform support is QR-only or uses a verified payment
    integration.
-   Whether support actions are recorded and how confirmation is
    established.
-   Account deletion and data-retention schedule.
-   Search provider and location precision.
-   Notification provider, categories, and retry strategy.
-   Legal/accounting review requirements for financial workflows.

## 20. Final Principle

Treat this model as a privacy-first starting point. Make data ownership,
visibility, lifecycle, and authorization explicit. In particular,
protect donor information and verification evidence, keep public content
source-backed, and preserve the strict separation between direct
temple/trust donations and optional JainConnect operating-cost support.
